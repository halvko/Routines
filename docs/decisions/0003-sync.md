# 0003: Hand-rolled sync: an outbox on the device, one ordered log per user

Accepted, 2026-11-06.

## Decision

Replicache-style, written here (a few hundred lines), not a library:

1. The device applies a change locally through the core and appends it to an
   **outbox** (`{id, name, args, clientSeq}`).
2. It pushes the outbox to the server. The server applies each change with
   **the same core**, gives it the next number in that user's log, stores it,
   and tells the user's other devices.
3. Devices pull everything after the last number they have, take it as their
   new base, and replay their still-unsent changes on top.
4. Changes are idempotent by `(clientId, clientSeq)`, so retries are safe.

How data merges:

- **Routines and to-dos:** last write wins per field. Lists are ordered by
  sort keys, not array positions.
- **Runs:** an append-only event log per run; state is a fold over it. That
  covers step state (done, skipped) and the run's own structure after it
  starts: one-off steps added to it and where it is placed. The snapshot a
  run starts from is written once, by the device that started it, and never
  merged.
- **Deleting, abandoning and dropping never erase.** Sync has no hard
  delete: deleting a routine or to-do, abandoning a run or dropping a step
  sets a status field (with who and when), and that field merges like any
  other. So a drop on the phone and an edit on the laptop, made offline at
  the same time, both survive: the step ends up dropped, keeps the edit, and
  can be restored. Neither device's decision silently undoes the other's.
  Purging what was deleted long ago is a separate, explicit action.
- **The core never discards a change it cannot apply.** A change that no
  longer fits (its step is gone, its run was abandoned, it breaks a rule) is
  kept and shown to the user to resolve, never dropped quietly.
- **Resolving never blocks.** Conflicts, duplicates and changes the core
  could not apply appear as a quiet notice the user opens when they choose,
  like "sign in to sync" (0004). Until then each device keeps showing the run
  it was using; a device that had neither shows the earlier one.
- **Things that must be unique carry a natural key**, which the core on the
  server checks, not the device. Example: one Day run per date. Two runs with
  the same key are **not merged automatically**: each started from its own
  snapshot (other options, an older copy of the routine), so their step ids
  can differ and a merge could lose changes. The server keeps both, marks the
  later one as a duplicate, and the user resolves it (abandon one, or move
  what they need across). Carry-over from yesterday is keyed by step or
  to-do, so nothing is carried over twice.

The server is the source of truth; a device is a cache plus an outbox (iOS may
evict web storage). Losing the sign-in never costs local work; see 0004.

## Today's data

Nothing is migrated from the current app's `localStorage`: losing that data
when moving to the new app is accepted (owner's decision, 2026-11-22).

## Why

- One user, a few devices: real conflicts are rare and simple.
- One writer per user orders everything, so all devices converge.
- No library in the research fits: Zero has no offline writes, InstantDB is
  shutting down, PowerSync and Electric need Postgres and an always-on
  service, LiveStore is pre-1.0. CRDT libraries mainly pay off for
  collaborative text.

## Rules out

- Editing shared state without going through the core's `update`.
- Array positions as identity in synced data.
