# 0003: Hand-rolled sync: an outbox on the device, one ordered log per user

Accepted, 2026-11-06.

## Decision

Replicache-style, written here (a few hundred lines), not a library:

1. The device applies a change locally through the core and appends it to an
   **outbox** (`{id, name, args, clientSeq}`).
2. It pushes the outbox to the server. The server applies each change with
   **the same core**, gives it the next number in that user's log, stores it,
   and tells the user's other devices.
3. Devices pull everything after the last number they have, take it as their
   new base, and replay their still-unsent changes on top.
4. Changes are idempotent by `(clientId, clientSeq)`, so retries are safe.

How data merges:

- **Routines and to-dos:** last write wins per field. Lists are ordered by
  sort keys, not array positions.
- **Runs:** an append-only event log per run; state is a fold over it. That
  covers step state (done, skipped) and the run's own structure after it
  starts: one-off steps added to it and where it is placed. The snapshot a
  run starts from is written once, by the device that started it, and never
  merged.
- **Deleting and dropping never erase.** Sync has no hard delete: deleting a
  routine or to-do, or dropping a run or step, sets a status field (with who
  and when), and that field merges like any other. So a drop on the phone and
  an edit on the laptop, made offline at the same time, both survive: the
  item ends up dropped, it keeps the edit, and it can be restored. Neither
  device's decision silently undoes the other's. Purging what was deleted
  long ago is a separate, explicit action.
- **Things that must be unique carry a natural key**, and the core on the
  server enforces it, not the device. Example: one Day run per date. If two
  devices each start today's Day offline, the server keeps one run for that
  date and folds the second one's events into it, and carry-over from
  yesterday is keyed by item, so nothing arrives twice.

The server is the source of truth; a device is a cache plus an outbox (iOS may
evict web storage). Losing the sign-in never costs local work; see 0004.

## Getting today's data in

The routines, runs and to-dos already in the app's `localStorage`
(`routines.v1`) are the owner's source of truth until the server takes over.
The new app imports them once, through the core (so old data is normalized
the same way it is today), and the import is idempotent, so running it twice
does not duplicate anything. How that data travels from the old address to
the new one is in 0005.

## Why

- One user, a few devices: real conflicts are rare and simple.
- One writer per user orders everything, so all devices converge.
- No library in the research fits: Zero has no offline writes, InstantDB is
  shutting down, PowerSync and Electric need Postgres and an always-on
  service, LiveStore is pre-1.0. CRDT libraries mainly pay off for
  collaborative text.

## Rules out

- Editing shared state without going through the core's `update`.
- Array positions as identity in synced data.
